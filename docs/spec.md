# np-aspire — Project Spec

Status: early draft. Sections marked **TBD** are open decisions.

This repository is the **Angular frontend** of np-aspire: an Nx monorepo of Angular apps and libraries. The backend lives in **[np-aspire-api](https://github.com/natepaxton/np-aspire-api)**: the .NET API, the Aspire AppHost that orchestrates it, and the Auth0 configuration (Terraform and the permissions manifest). Its `docs/spec.md` covers those parts.

Until 2026-09-17 both lived here. The combined state is tagged **`pre-api-split`**. The .NET history was moved to np-aspire-api with `git filter-repo`.

## 1. Goal

An Nx monorepo for Angular apps and shared libraries. The apps call the np-aspire-api backend under `/api/v1/...`. How they are packaged and hosted in production is decided later (§6).

## 2. How the frontend fits the system

```
 Browser ──── login ────► Auth0
    │  HTTP + Auth0 access token
    ▼
 Angular app ──/api/v1/...──► API (np-aspire-api, orchestrated by Aspire)
```

- Apps call the backend with **relative URLs** (`/api/v1/...`) and never use hardcoded hosts or ports.
- **There is no gateway for now.** np-aspire-api defers NGINX until it has multiple APIs. Keeping relative `/api/v1/` URLs means adding one later needs no frontend changes.
- **Local development:**
  - Run the backend in np-aspire-api with `dotnet run --project src/NpAspire.AppHost`.
  - Run `npx nx serve sandbox` here. The dev server's proxy config (`apps/sandbox/proxy.conf.mjs`) forwards `/api` to the API, so the browser sees one origin and no CORS setup is needed.
  - The proxy target defaults to `http://localhost:5104`, which is the API's port when it runs standalone. Under the Aspire AppHost or Docker Compose the API gets an assigned port instead, so pass it: `API_URL=http://localhost:<port> npx nx serve sandbox`. Setting `API_URL` in the workspace's gitignored `.env.local` also covers e2e runs, because `playwright.config.mts` loads that file before starting the dev server.
- **Production hosting** (same-origin proxy vs. CORS, TLS, and how the app is packaged) is **TBD**. It will be decided with np-aspire-api's deployment target (§6).

## 3. Components

### 3.1 Projects

| Project       | Type           | Purpose                                                                                                                                                                                                 |
| ------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sandbox`     | app            | Developer test bed. It gets quick, minimal UI for exercising API endpoints as they are built. It is not production UI. Serves on port **4300**.                                                         |
| `sandbox-e2e` | Playwright e2e | End-to-end tests for `sandbox`.                                                                                                                                                                         |
| `ui`          | library        | Shared app-level components (composed from helm primitives), plus the shared theme and Tailwind entry styles. Import path `@np-aspire/ui`.                                                              |
| `helm-*`      | libraries      | spartan/ui **helm** components, generated by the Spartan CLI into `libs/helm/<name>`. This is our code to edit, and one Nx lib per primitive (project `helm-<name>`, import `@spartan-ng/helm/<name>`). |
| `auth`        | library        | Auth0 setup (`provideNpAuth()`, import path `@np-aspire/auth`, tagged `type:ui`). The HTTP interceptor and the permission helpers arrive with the generated API client (milestone 2).                   |

### 3.2 Standards

- Latest stable Angular, generated with the `@nx/angular` generators.
- Standalone components, signals, `OnPush` change detection, and built-in control flow (`@if`, `@for`).
- **UI library: spartan/ui** (MIT). It has two layers:
  - **brain:** headless, accessible primitives installed from npm as `@spartan-ng/brain`.
  - **helm:** Tailwind-styled components, copied into `libs/helm/`, that we own and edit.
  - **Style: Mira** (Spartan's compact design-system style), with **base color: neutral**. The style and the base color are separate settings.
  - The CLI reads `components.json` in the workspace root:
    ```json
    {
      "componentsPath": "libs/helm",
      "style": "mira",
      "importAlias": "@spartan-ng/helm",
      "generateAs": "library",
      "buildable": true
    }
    ```
    Keep this file committed, so every `nx g @spartan-ng/cli:ui` run uses the same style and location without prompting.
  - Add components with `npx nx g @spartan-ng/cli:ui <name>`.
  - Upgrade with the CLI's `migrate-*` and `healthcheck` generators.
  - Alternatives considered: Angular Material (rejected, to get a different look), PrimeNG (rejected: now a commercial license with a key-gated free tier), Taiga UI, NG-ZORRO, and the Angular CDK or Angular Aria with custom styling.
- **Styling: Tailwind CSS v4 + SCSS.**
  - Tailwind handles layout and utility styling in templates.
  - The Spartan theme (CSS variables) is the single source of truth for design tokens: colors, radius, and so on. Don't duplicate tokens as SCSS variables.
  - **SCSS stays the default for component styles** (set in the `nx.json` generator defaults).
  - Tailwind v4 must not go through Sass, so each app's **global** stylesheet is plain `styles.css`.
    - The shared entry is `libs/ui/src/styles/theme.css`. It holds the Tailwind layer imports, the Spartan preset, and the neutral theme variables. Tailwind's automatic source detection is turned off there (`source(none)`).
    - Each app's `styles.css` imports that file and declares `@source` paths for its own folder and for `libs/`.
    - PostCSS is configured once, in the root `.postcssrc.json`.
  - Component `.scss` files that need Tailwind's `@apply` must add `@reference` to the Tailwind entry. Prefer utility classes in templates over `@apply`.
- Unit tests use **Jest** (`jest-preset-angular`). Generate projects with `--unitTestRunner=jest`, because newer Angular and Nx versions may default to Vitest.
- Use Playwright for e2e tests. Each app gets its own `<app>-e2e` project.
- **Module boundaries** (ESLint, via project tags):
  - `type:app` may import `type:ui` and `type:helm`
  - `type:ui` may import `type:ui` and `type:helm`
  - `type:helm` may import `type:helm`
  - `type:e2e` may import nothing
  - Every project needs a tag.

### 3.3 Auth (Auth0, frontend side)

The API validates tokens and enforces all access rules (see np-aspire-api's spec §4–5). The frontend's part:

- **Login flow:** Authorization Code + PKCE through the Auth0 Angular SDK (`@auth0/auth0-angular`). Apps wire it up with `provideNpAuth()` from `@np-aspire/auth`, which holds the tenant settings in one place.
- **Tenant:** `nate-paxton.auth0.com`, SPA client `bMCqpBAFVb0NWPuHZp74Suxz9ggsADST`. Both values are public in a browser app, so they are plain constants in the `auth` library rather than build-time configuration; a second tenant would change that.
- **Audience:** the SPA requests tokens for the Auth0 **API** audience, `https://api.np-aspire.com`, so they are JWT access tokens. It is an Auth0 identifier, not an address the app calls — backend requests stay relative (§2).
- **Token storage:** tokens are kept in memory (the SDK default), with **refresh token rotation** (`useRefreshTokens`). Never `localStorage`. The API is created with `allow_offline_access` and the SPA client with rotating refresh tokens.
- **Cold starts need `useRefreshTokensFallback`.** The memory cache means the refresh token lives in a web worker that dies with the page, so after a reload the SDK has nothing to refresh with and throws `Missing Refresh Token`. The fallback lets it get a fresh pair from the hidden iframe (`prompt=none`) using the Auth0 session cookie. That path depends on third-party cookies, so an **Auth0 custom domain** will be needed before it is dependable outside dev (§6).
- **Interceptor:** the Auth0 HTTP interceptor's `allowedList` covers only the API, so tokens are never sent anywhere else. `provideNpAuth({ apiBase })` derives the list from the API base; each app registers `authHttpInterceptorFn` with its own `provideHttpClient`.
- **One API base per app.** The app owns it (`apps/sandbox/src/app/api.ts`) and passes it to both `provideNpAuth()` and the `API_BASE_URL` token its HTTP calls use, because an allowlist that disagrees with the URLs actually called attaches no token and fails as unauthenticated. Empty means same-origin through the dev proxy, which is today's setting; an absolute origin would make the calls cross-origin and need CORS on the API (§6). When the generated client lands it should take its base from the same token.
- **Route guards** (`authGuard`) are for user experience only. They are not security.
- **Angular never decides access and never decodes access tokens.** It shows or hides UI based on the `permissions` returned by `GET /api/v1/users/me`.
- **Roles** (defined in np-aspire-api):
  - `member`: `read:profile`, `update:profile`. Auto-assigned on first login.
  - `admin`: adds `read:users`.
  - A user with no role gets 403 from the API.
- **Permission names are never hand-typed.** They come from the API contract (§3.4).
- **Everything on the Auth0 side** — the SPA client, the API and its permissions, the roles, the post-login default-role action, and the dev test users — is managed by Terraform in np-aspire-api (`infra/auth0`), never in the dashboard. The callback, logout, and web-origin URLs are `http://localhost:4300`, with no trailing slash, which is exactly what the SDK sends as `window.location.origin`.

### 3.4 API contract

- np-aspire-api serves an OpenAPI document. It is the contract between the repositories.
- The frontend **generates** its API client and types from that document, including the permission names, which the API exposes as an enum. Hand-written API types are not used, because nothing else keeps the two repos in sync.
- Generator and document source: **TBD** (§6).

## 4. CI and repository settings

**GitHub Actions** (`.github/workflows/ci.yml`) runs on PRs into `main` and on pushes to `main`. A newer push cancels an in-progress run for the same branch.

- **`Lint, test, build` job:**
  1. `nx format:check`
  2. `nx affected -t lint build`
  3. `nx run-many -t test --configuration=ci`. All projects are tested so Codecov always gets a complete report. Revisit (affected tests plus Codecov carryforward flags) if test time grows.
  4. Coverage table written to the job summary (`tools/scripts/coverage-summary.mjs`).
  5. Upload to Codecov, and upload coverage reports as an artifact.
- **`E2E` job:** `nx affected -t e2e`, with Playwright browsers cached by version. The Playwright report is uploaded on failure.
  - The step gets `E2E_TEST_USER_PASSWORD` from the repository secret. The login tests skip themselves when it is empty, so forks still pass.
  - They also skip when the API is not answering, which is the case in CI today: no backend runs there yet. **TBD** (§6).
- Shared job setup lives in `.github/actions/setup`: Node from `.tool-versions` (which asdf also uses locally), `npm ci`, and `nx-set-shas`.
- Nx Cloud is not used (`NX_NO_CLOUD=true`).
- **Later additions:**
  - an API-client drift check (milestone 2)

**Code coverage**

The test tools enforce the minimums, so CI and local runs fail the same way. Codecov adds reporting.

| Scope                                          | Lines / statements / functions | Branches |
| ---------------------------------------------- | ------------------------------ | -------- |
| Shared libraries (`ui`, …)                     | 80%                            | 75%      |
| `sandbox` (developer tool)                     | 60%                            | 50%      |
| Changed lines in a PR (Codecov `patch` status) | 80%                            | —        |

- Jest (Istanbul) enforces the minimums with `coverageThreshold` in each project's `jest.config.cts`.
- `collectCoverageFrom` lists all source files, so a file with no tests counts as uncovered.
- Reporters: `lcov` (for Codecov), `json-summary`, and `text-summary`.
- **Excluded from coverage:**
  - `libs/helm/**`
  - `main.ts`, `app.config.ts`, `*.routes.ts`, and `index.ts` barrels
  - generated `*.g.ts` files and generated API clients
- **Codecov (`codecov.yml`):**
  - `project` status: overall coverage may not drop by more than 1%.
  - `patch` status: changed lines must reach 80%.
  - One component per project.
  - Uploads use the `CODECOV_TOKEN` secret, stored as both an Actions secret and a Dependabot secret.
  - **Every new project with tests needs** a `collectCoverageFrom` and threshold in its Jest config, and a Codecov component.

**Branch protection on `main`** (public repository, applied with `gh api`):

- Changes go through a PR. No approvals are required, because this is a solo project; stale reviews are dismissed.
- Required checks: `Lint, test, build`, `E2E`, `codecov/patch`, and `codecov/project`.
- The branch must be up to date with `main` before merging.
- Review conversations must be resolved.
- No force pushes or deletions.
- The rules apply to admins too.

**Secrets**

| Secret                   | Used by                    | Stored as                          |
| ------------------------ | -------------------------- | ---------------------------------- |
| `CODECOV_TOKEN`          | the coverage upload        | Actions secret + Dependabot secret |
| `E2E_TEST_USER_PASSWORD` | the Playwright login tests | Actions secret + Dependabot secret |

`E2E_TEST_USER_PASSWORD` is the dev-tenant test users' password — the same value as np-aspire-api's `TF_VAR_test_user_password`, which is what creates those users. Both secrets need the Dependabot copy as well, because Dependabot PRs run with a separate secret store and both `Lint, test, build` and `E2E` are required checks. Locally the password comes from a gitignored `.env.local` in the workspace root, which `playwright.config.mts` loads with Node's `process.loadEnvFile`.

**Secret scanning:** secret scanning and push protection are enabled (free for public repositories). The optional non-provider patterns and validity checks require GitHub Secret Protection (paid), so they stay off.

**Dependabot**

- **Alerts and security updates:** enabled in the repository settings. Security fixes arrive as one grouped PR.
- **Version updates** (`.github/dependabot.yml`):
  - Checked every Monday at 06:00 America/New_York, with at most 5 open PRs per ecosystem.
  - New npm releases wait 3 days before being proposed (7 days for major releases).
  - Ecosystems: `npm` and `github-actions`.
- **npm groups:** `nx`, `angular`, `ui-styling` (Spartan, Tailwind, PostCSS), and `minor-and-patch` for everything else. Other majors arrive as individual PRs.
- **Majors Dependabot ignores**, because they are upgraded with tooling that also migrates code:
  - Nx and Angular (`npx nx migrate latest`)
  - Spartan (the CLI's `migrate-*` generators)
  - `typescript` and `@types/node`, which follow Angular and Node
- **npm install-script approvals:**
  - `allowScripts` entries are name-only (`.npmrc`: `allow-scripts-pin=false`), so version bumps don't un-approve build tools.
  - A dependency that adds a _new_ install script still needs `npm approve-scripts <pkg>`.
  - Currently approved: `nx`, `esbuild`, `lmdb`, `@parcel/watcher`, `unrs-resolver`, and `msgpackr-extract`. `fsevents` is denied because its prebuilt binary is used.

## 6. Open decisions

- **API client generation:** the generator (for example `ng-openapi-gen` or `@hey-api/openapi-ts`), and where the OpenAPI document comes from: a copy committed and checked in CI, a release artifact from np-aspire-api, or a running API.
- **Production hosting and packaging:** how the built apps are served (static hosting, a container image, or behind a future gateway) and whether that is same-origin with the API. It is decided together with np-aspire-api's deployment target.
- **An Auth0 custom domain:** the silent-iframe fallback that covers cold starts relies on third-party cookies, which browsers increasingly block (Safari already does, and the e2e suite runs WebKit). A custom domain makes the Auth0 origin first-party. It would be Terraform in np-aspire-api.
- **An API for the E2E job:** the login tests need a running backend, and CI has none, so they skip there. Options are starting np-aspire-api's container in the workflow, pointing at a deployed dev environment, or leaving those tests local-only. It depends on the deployment target above.

### Milestone 1 — Frontend workspace scaffold ✅

- The workspace was created with `nx init` plus the `@nx/angular` generators. The `create-nx-workspace` Angular preset now produces a demo template, so it wasn't used.
- `sandbox` serves on port **4300**, to avoid clashing with other local Angular apps on 4200.
- `sandbox` has a minimal shell (sidebar nav and a lazy-loaded Home page) and uses the shared `Panel` component (`ui-panel`, a titled card with a footer slot).
- spartan/ui was initialized with `npx nx g @spartan-ng/cli:init --project=sandbox --theme=neutral`. The generated theme was moved into `libs/ui/src/styles/theme.css`.
- Helm primitives `button`, `card`, `input`, and `utils` were generated. Spartan named them without a prefix, so they were renamed `helm-<name>` and tagged `type:helm`. `nx lint --fix` corrected their generated `package.json` peer dependencies.
- Playwright smoke tests check the shell, the theme, and a form interaction in Chromium, Firefox, and WebKit.

### Milestone 2 — Auth0 SDK login ✅ (partial)

- `libs/auth` (`@np-aspire/auth`, tagged `type:ui` so apps and `ui` may import it) exports `provideNpAuth()`, which calls the SDK's `provideAuth0()` with the tenant, the SPA client ID, `redirect_uri: window.location.origin`, the `https://api.np-aspire.com` audience, and `useRefreshTokens`.
- `sandbox` adds `provideNpAuth()` to its app config, log in / sign up / log out controls in the sidebar, and a `/profile` page that renders the signed-in user's claims.
- The Auth0 application's callback, logout, and web-origin URLs are `http://localhost:4300`. Anything served from another origin fails the callback, so the sandbox's port 4300 is now load-bearing.
- No Auth0-side work was needed: np-aspire-api's Terraform already provisioned the API (with `allow_offline_access` and RBAC), the roles, and the test users. `terraform -chdir=infra/auth0 plan -var-file=env/dev.tfvars` reported no changes on 2026-09-17.
- The `/api/*` interceptor is wired: `provideNpAuth()` sets the `allowedList`, `sandbox` registers `authHttpInterceptorFn` with `provideHttpClient`, and `apps/sandbox/proxy.conf.json` forwards `/api` to `http://localhost:5104` in dev. The Home page's "API auth check" panel calls `GET /api/v1/auth/check` to exercise it end to end.
- `apps/sandbox-e2e/src/auth.spec.ts` signs in as each test user through real Universal Login and calls `GET /api/v1/auth/check`. **All three get 200, including `test-norole`:** that endpoint is plain `[Authorize]`, so it asks for a valid token, not for a permission. Roles are not yet distinguishable from the frontend; the 403 case needs an endpoint behind a permission policy, which arrives with `UsersController`.
- Those tests are Chromium only, to keep it to three real logins per run, and skip when `E2E_TEST_USER_PASSWORD` is unset or the API is not answering — so they pass locally with the backend up and skip in CI until it has one (§6).
- The tenant serves the **Classic** Universal Login (the Lock widget), so the login helper uses role-based locators (`Email`, `Password`, `Log In`) that also fit the New experience if the tenant switches.
- Still open (with the API client): permission helpers and route guards.

## 8. Deferred

- **Production packaging and hosting** for the apps, such as a static-site image or static hosting. It follows np-aspire-api's deployment-target decision.

- **Remove the `smol-toml` npm override** (`overrides` in `package.json`) once Nx itself depends on `smol-toml` ≥ 1.7.1. It was added to fix Dependabot alert #1, a denial-of-service issue in `smol-toml` ≤ 1.7.0, because `nx@23.2.1` pins 1.6.1. To check: `npm ls smol-toml` shows the version Nx requests.
- **In-app role management UI.** It depends on np-aspire-api's deferred Management API support.
